# AI 交接：在游戏上扩展 → 试玩验证 → 再抽离到引擎

> 这是本项目的核心开发纪律。新对话的 AI 必须先读完本文档再动手。
> 已加载项目 skill `tge-game-prototyping`、且本会话已读过下列材料时，不必重复读。

## 0. 先读懂现状（动手前必读，不许凭想象）

按顺序读：
1. `README.md` —— 数据模型、5 个 JSON 结构、避坑清单、能力缺口、QA 用法。
2. `games/demo_minimal/README.md` 与 `games/demo_minimal/*.json` —— 最小可玩 demo（3 场景+1 战斗），
   是"用引擎做游戏"的标杆样例。
3. 当前 `game_data/` 里实际加载的工程（用 `tools/load_game.ps1` 切换）。
4. 需要了解某机制细节时再查 `engine/` 对应模块和 `app.py` 路由，不要猜。

读完先用自己的话复述：数据模型、引擎能力边界、两阶段纪律（见下）。

## 1. 铁律：两阶段，不许跳步

```
阶段一【游戏内原型】          阶段二【抽离到引擎】
为「这一款游戏」做最小实现  →  用户试玩确认好玩  →  泛化成通用能力进 engine/
允许游戏专用的硬编码              （必须有用户确认）      配置化 + 编辑器 + QA + 文档
```

- **没有用户"试玩通过"的明确确认，禁止进入阶段二。** 不要因为代码写完了就自作主张抽引擎。
- **试玩通过 ≠ 立即抽离**：通过后机制进入「已验证·待抽离池」，允许攒多个模块后由用户
  拍板批量抽离（规则见 §4）。用户没说"开始抽离这批"之前，池里的模块一律留在游戏工程。
- 阶段一也**禁止过度设计**：不要为"以后别的游戏可能用到"提前抽象（M1 的教训）。
  只解决眼前这款游戏的需求，越具体越好。
- 每次只推进一小块，阶段一结束要给用户一个**可立刻玩到**的版本。
- **同时存活的未抽离原型建议不超过 5 个**；原型之间禁止互相 import/共享私有状态，
  各自独立模块、独立 `_proto_` 配置、独立 smoke，保证抽离时可逐个干净拆除。

## 2. 怎么判断一个需求走哪条路

| 需求 | 阶段一怎么做 |
|---|---|
| 纯内容（新场景/NPC/敌人/物品/对话/事件） | 只改对应游戏工程的 JSON，**不碰任何 .py/.js** |
| 现有效果能拼出来的玩法（flags+条件对话+事件） | 用数据拼，不写代码 |
| 引擎不支持的新机制（技能/逃跑/多敌人/经验/限量商店/任务 UI 等） | 写**游戏专用**的最小代码原型，并清楚标注（见 §3） |

引擎当前**明确不支持**（需要阶段一原型）：技能、防御行动、逃跑、多敌人同场、
经验/升级、限量商店、任务日志 UI、物品配方/建造。完整清单见 README「引擎现状缺口」。

## 3. 阶段一原型的隔离要求（为日后抽取做准备）

当不得不写代码时：
- 新机制尽量**自包含**：独立模块/独立函数，通过清晰的输入输出接入，
  不要把游戏专用逻辑散落到多个引擎文件里。
- 所有游戏专用、尚未泛化的代码用统一注释标注：
  `# PROTOTYPE-GAME：<机制名> —— 待试玩验证后抽离，勿当通用API`
- 数据契约里游戏专用字段加前缀或集中放置，便于阶段二识别。
- 原型配套固化冒烟脚本 `games/<工程>/<机制>_smoke.py`（参照
  `games/demo_minimal/proto_retreat_smoke.py`）：**长期保留、随机制迭代直接改、
  同一条命令反复跑**，禁止用完即删、下轮重新生成。阶段二抽离时其断言迁入 `qa/m*.py`。
  **2026-10-05 起新约定**：新模块默认不再编写 smoke，试玩验收由用户负责；
  已有 smoke 只改不删。
- 阶段二抽离时要能做到：删掉标注代码后游戏行为不变（被通用实现替换）。

## 4. 阶段二抽离的准入条件与清单

**准入（全部满足才做）**：
- 用户已实际试玩并明确说"这个机制保留/好玩"；
- 机制在游戏里至少跑通过一条完整链路，边界（失败/取消）也试过；
- 已想清楚"别的游戏会怎么用"，不是只为这一个数值/文案服务。

**批量抽离（攒池子模式）**：
- 允许攒多个已验证模块后一次抽离，建议同主题打包（如"战斗深化"一批）或 2~4 个一批，
  由用户明确说"开始抽离这批"启动。
- 池里每个模块都必须已单独满足上述准入；抽离时逐模块过下面清单、逐个验证，
  不要把多个机制的改动揉成一次提交级别的大改动。
- 一批抽完：该批 PROTOTYPE 标注与原型文件清零、游戏行为被通用实现等价替换、
  各 smoke 断言迁入 `qa/m*.py`。demo_minimal 随之恢复"纯 JSON 标杆"身份。

**抽离清单（每个模块各过一遍）**：
1. 去掉游戏专用硬编码，改成数据驱动（JSON 配置 / 通用参数）。
2. 引擎层：`engine/` 模块 + `app.py` 路由/事件接线（如需）。
3. 可视化编辑器同步支持（表单或画布），后端补引用校验与删除保护。
4. QA：新增/扩展 `qa/m*.py` 用例，最后 `python -m qa.run_all` 全绿。
5. 文档：更新 `README.md` 数据模型与能力缺口；移除 PROTOTYPE 标注。
6. 不破坏既有回归（当前基线 172/173，唯一失败为酒馆工程既有数据偏差）；在线模式仍冻结（见 §6）。

## 5. 日常工作流（Windows / PowerShell）

- 工程切换（仓库根目录；脚本刻意纯 ASCII）：
  - 加载：`powershell -ExecutionPolicy Bypass -File .\tools\load_game.ps1 -Game <工程名>`
  - 还原：`powershell -ExecutionPolicy Bypass -File .\tools\load_game.ps1 -Restore`
- 改完 JSON 先离线自检：`.\.venv\Scripts\python.exe tools\validate_game_data.py games\<工程>`
- **改 `games/<工程>/` 的 JSON 后必须重新跑 `load_game.ps1 -Game <工程>` 再重启**——
  app.py 只读 `game_data/` 副本，源目录改动不会自动生效（2026-10-05 踩过：Boss 加了
  但洞穴看不到）。proto_*.py 代码不受此影响（import 自源目录）。
- 切换工程/改了启动期数据后**必须重启 app.py**（数据只在启动时读入内存）。
- 访问：玩 `http://127.0.0.1:5000/static/index.html`；
  编辑 `http://127.0.0.1:5000/static/editor.html`。
- 控制台调试：`reset / teleport <场景> / set_flag <名> / give <物品> / add_item`。
- 跑回归：`.\.venv\Scripts\python.exe -m qa.run_all`。
- 发 JSON 用 UTF-8 字节，中文不要走 PowerShell 命令行字面量；`.ps1` 保持纯 ASCII。
- **不要主动 `git commit`**，除非用户明确要求。

## 6. 硬约束（任何阶段都不许违反）

- 在线模式冻结：不新增/重构在线/隔离层（session_manager、save 双轨、auth），
  QA 只测离线；改 NPC/对话/事件/配置不影响进行中的游戏（热更新边界见 README）。
- 多会话存档隔离键（离线 client_id、在线 user_id）不能动。
- 游戏 JSON 里不放坐标；坐标是编辑器独立的 `npc_layouts.json`。
- 出口是单向的（新增出口不自动加返程），这是锁剧情的设计不是 bug。
- 玩家命中 = 武器 damage − 敌防；玩家自身 attack 属性不参与（别设计靠攻击力的玩法）。

## 7. 本次任务的沟通方式

- 每个阶段开始前先用 3~6 行说明：要解决什么、动哪些文件、属阶段一还是阶段二。
- 阶段一完成后停下，给试玩路径和验证点，**等用户确认**再谈抽离。
- 拿不准某机制该用数据拼还是写代码时，先问用户，不要直接动引擎。

## 8. 省钱与提效约定（降低对话成本，提高交互频率）

目标：把 token 和轮次花在机制设计与实现上，可省的仪式一律省略；能由用户代办的
命令不抢着做。

**验证分工**
- 视觉、交互、手感**一律由用户试玩判断**（AI 不做浏览器画面测试）；AI 只负责
  数据校验、API 级冒烟、回归测试。
- 用户说「我来跑」时，AI 只给命令并等待结果，不代执行——切工程、重启 app.py、
  跑冒烟、跑回归都可以由用户代办。

**按需验证，不跑全套仪式**
- 只改游戏 JSON：跑 `validate_game_data.py` 即可。
- 只改原型模块或其接线：跑该原型的固化冒烟脚本即可。
- 纯删代码/文案/前端微调，且未碰 `engine/` 与 `app.py` 共享路径：说明理由后
  可跳过 `qa.run_all`。
- 只有动了 `engine/` 或 `app.py` 共享路径，才还原酒馆工程跑全量回归。
- 已确认过的既有失败不重复排查、不重复汇报（当前基线 **172/173**：M5
  `sprite-has-key-greeting` 是酒馆数据与用例断言的既有偏差）。
- 只改前端静态文件时刷新浏览器即可，不必重启后端；改启动期数据或 .py 才重启。

**沟通密度**
- 规则决策点用一次提问批量问清（最多 4 个），不要一问一答挤牙膏。
- 不复述文档、不贴大段代码；阶段交付只给：试玩路径、验证点、改动文件表、
  测试结果数字。
- 小步快跑：一次只推进一个机制点，每个交付版本必须立即可玩。
- 不要被单个问题卡住；超过一轮仍无定论就带着 2~3 个具体选项问用户。
